# Azure Functions CLI v5: Release Readiness

**Status:** PROPOSAL - FOR TEAM REVIEW.

This package helps the CLI team review the remaining work and release requirements
for CLI v5. Milestones, priorities, and scope in these documents are proposals
until the team agrees on them.

## Review This Package

1. Open the [roadmap](./v5-ga-readiness/roadmap.md) for proposed issue placement,
    Issues Needing Input, Needs Triage and requirements that need clearer tracking.
2. Use the [decisions](./v5-ga-readiness/decisions.md) to resolve scope,
   architecture and release choices, including consequences of proposed cuts.
3. Check each choice against the protected release requirements below.

## Protected Release Requirements

Feature completeness is not GA readiness. Reduce feature breadth before lowering
quality, security/privacy, required distribution, compatibility or release safety.
Every advertised workflow needs passing acceptance evidence or an explicit,
accepted gap with supported migration guidance.

An assigned issue or green PR alone does not establish readiness. Confirm delivery,
review and release owners; estimates help planning but do not qualify a release.

## CLI Quality

Use pinned Preview 3 artifacts and repeatable package/profile/fixture inputs as
the baseline. Compare exit codes, structured output, configuration
semantics, startup/invocation, errors, cleanup and relevant filesystem effects.
Require exact wording or generated bytes only where a contract requires them.
Declare intentional changes alongside the affected scenarios.

Classify results as unchanged pass, expected change, regression, new capability,
baseline limitation or inconclusive. New capabilities and baseline limitations
need passing candidate acceptance checks, not invented baseline passes. Do not
accept unexplained regressions or inconclusive runs as green.

Use representative real-CLI smoke, behavioral and local end-to-end scenarios in
PR validation, with the managed emulator where appropriate. Qualify required
cloud-dependent workflows separately; do not exclude them from release coverage.
Measure startup, common commands and shutdown against reviewed limits.

Keep results reproducible: record commands, platform, installation, inputs, output
and exit code. Add permanent regression checks for failures. Isolate CLI test state
with `FUNC_CLI_HOME` and clean up owned processes/resources.

## CLI-To-Template Functional Tests

[#5656](https://github.com/Azure/azure-functions-core-tools/issues/5656) covers
representative CLI functional testing for `func init`, `func new`, and
`func quickstart`. Core Tools validates selection, arguments/options, invocation,
successful creation, minimum semantic observables and appropriate failures.
The Templates repository primarily owns detailed generated-content correctness;
CLI scenarios need not exhaustively validate every template payload.
Keep #5656 separate from broader Preview 3 vs current CLI regression coverage.

Retained template migration needs a complete acquisition, context, listing,
selection and invocation path, strict parameters, actionable diagnostics and
fail-closed mandatory constraints. `--force` may handle file conflicts, not bypass
eligibility. An existing-provider fallback needs tested behavior and clear limits;
internal catalog work alone is not a completed user experience.

## Compatibility And Trust

Define the advertised platform/stack/channel combinations explicitly, not an
assumption that every combination is supported. Install and run each supported
combination with pinned host, worker, bundle, template and profile inputs. RID
pointers must acquire the mapped implementation at the exact selected version
from the intended source.
Reject known incompatibilities within the agreed contract with actionable errors;
do not promise enforcement of every unknown future combination.

Check token handling, publisher/package trust, signatures, feed selection and
supply-chain mitigations before accepting or extracting untrusted content.
Profiles need reproducible versions, named publishers/operators and tested
correction paths that leave shipped inputs unchanged.

## Privacy And Diagnostics

Supported failures and runtime diagnostics must be actionable without corrupting
machine-readable output or leaking secrets. If telemetry export ships, qualify
its actual content/scrubbing, opt-out, destination/retention, lifecycle and offline
latency. If disabled, verify no-export behavior. Deferring export does not waive
privacy or diagnostics. CLI telemetry uses its build-injected sink; it does not
change customer connection-string precedence.

## Safe Updates And Distribution

The [release design](./cli-release-story.md) identifies CDN/install scripts,
Homebrew, winget and npm as GA-blocking; npm includes both `azure-functions-cli`
and `azure-functions-core-tools`. APT is post-GA. Detecting other package managers
does not promise those channels. MSI's role in winget remains a decision.

Qualify install, pin, upgrade and recovery paths for the supported targets.
Verify integrity before extraction, signing for every downloadable artifact,
macOS notarization and user verification guidance. A signing pipeline alone does
not prove artifact trust. Respect package-manager-owned files.
If in-place updating is retained, test serialization, cancellation, backup,
replacement probing and rollback; otherwise qualify a supported manager/installer
update and recovery path. Do not ship an unsafe or unexplained update dead end.

## Release Evidence And Rollback

Record selected source/version, artifact hashes/signatures, payload/profile inputs
and environment before tests, then add results before promotion. Stage inputs,
qualify them, and only then advertise the release. Published CLI artifacts and
their required workloads/profiles must be available together.

Qualify the exact final GA version, signed bytes and channel packaging. Rebuilds,
version/suffix changes, re-signing or changed wrappers require the affected checks
again; an earlier RC checksum does not qualify replacement bytes. GA publication
is not another implementation phase. Execute a prepared human go/no-go, cutover,
verification, known-issue acceptance and operational/support handoff.

Use roll-forward-first correction without retagging or mutating shipped versions.
Unlist bad workload versions, never delete versions already resolved by users.
Rehearse actual CDN manifest/cache, channel, profile and workload correction paths
with pinned previous versions; a written policy is not a tested playbook.

## Migration, Partners And Accessibility

Record language/tooling parity as supported, changed with guidance or deliberately
excluded with rationale. Validate current `host.json`/`local.settings.json`
compatibility and supported alternatives before approving workflow cuts. Close
required partner/CI adoption blockers and the v4 support/migration position.
Audit NO_COLOR, non-TTY/redirected output, prompts, cancellation and assistive use.
Localization and additional tooling remain scope decisions, not implied promises.

## Documentation Readiness

Review documentation affected by CLI v5 and update current guidance where needed.
Preserve historical planning material where useful, but do not present superseded
plans as current release guidance. Cover runtime/workload authoring, output and
configuration contracts, installation/update, release procedures, migration and
final-version notes. The broader Core Tools documentation audit is separate
follow-up work.

Supporting references: [earlier scope inventory](./v5-ga-plan.md),
[component release process](./vnext-release-process.md) and
[update design](./func-update.spec.md). Use them with the agreed current scope,
not as proof that every intended feature is mandatory or already implemented.
