# Bundled native .NET templates

The physical .NET workload contains `tools/any/templates/dotnet.nupkg`, a
`FuncTemplate` adapter package, and a root `bundled-templates.json` declaration
generated by the existing workload SDK task from the actual archive. No new
template feed, companion release, catalog or package-admission exception is used.
The inner version follows the physical stack version.

`upstream-sources.json` pins the original NuGet archives by ID, version and
SHA-256. Item templates use the existing `Workloads.Templates.DotNet` baseline,
4.0.5590. Project templates use the available 4.0.5337 baseline, which contains
both C# and F# isolated projects with `net10.0` support. This is not a claim that
the legacy unversioned project-template installer always resolved that version.
The original packages declare package type `Template`; the adapter declares
`FuncTemplate` rather than relaxing native package validation.

Packing validates both upstream archive digests and retains both original
nuspecs under `provenance/`. Except for the qualified source, binding-literal and
F# Cosmos selector adaptations described below, upstream `content/` bytes are unchanged. It adds
`func.host.json` files, including `--target-framework` / `-tfm` aliases for the
native project `Framework` parameter. The repository MIT license has the same
copyright and grant as upstream's `LICENSE.txt`; its pinned source URL is in
the provenance declaration. Original nuspec license metadata is retained, not
rewritten as evidence of a different upstream release.

The raw inventory is 36 items (29 C#, 7 F#) plus 2 projects (C#, F#). Those are
native configuration records, **not deduplicated CLI-visible counts**.
Template identities, group identities, existing short names, parameter contracts, conditional
sources, generated values, package versions, post-actions and unadapted source
files are preserved, including F# project ordering and `_gitignore` renaming.

The F# Cosmos item additionally declares the public compatibility selector `cosmos`
in native `shortName` metadata, retaining `CosmosDB`. Both select
`Azure.Function.FSharp.Isolated.CosmosDBTrigger.4.x` in an F# project; C# `cosmos`
continues to select the C# item. Original configuration bytes remain in provenance.
The new configuration and the earlier literal-encoded configuration are separately
pinned to the same reviewed F# source; adding an alias to arbitrary configuration
bytes does not qualify it for literal encoding or bypass owner, language or type checks.

## Scoped C# database supporting types

The pinned SQL and MySQL output/trigger items each declare a namespace-level
`ToDoItem`. Adding distinct functions from these templates could therefore
make a previously compiling project fail with duplicate types. This is an
inherited upstream limitation, not evidence of a native migration regression.

Packing adapts only the four source files in `supporting-types.json`, after
checking their identity, original configuration, exact source path and SHA-256.
It nests the DTO inside its owning new function class and names it
`<FunctionName>Item`, using the existing native `sourceName` substitution for
every type reference. Nesting avoids collisions with other functions and
existing user DTOs; the suffix also permits a function named `ToDoItem`.
Namespaces, connection-string values and package dependencies remain unchanged.
The supporting-type adaptation does not change configurations, SQL/MySQL input
items or F# sources. No existing project source is inspected or rewritten.

The original four source files remain byte-for-byte under
`provenance/upstream-content/content/`; the source pins are also packaged in
provenance. Unknown or changed upstream inputs fail packing rather than
receiving a best-effort text rewrite. This changes the shape of newly generated
example DTOs only; it does not migrate previously generated functions.

The same exact-source pins qualify two additional authoring corrections.
The MySQL trigger's source placeholder is `table`, matching its unchanged
native parameter, instead of `table1`. Omitted `--table` now produces `table1`,
not `table11`, and explicit values are not suffixed with `1`. SQL/MySQL input
and output bindings and the SQL trigger retain their existing parameter maps.
The SQL trigger logs its sample changes using the framework's
`System.Text.Json` serializer instead of an undeclared `Newtonsoft.Json`
dependency. The sample retains its JSON property names, numeric operations,
row values and nulls; equivalent JSON escaping need not be byte-identical.
Neither correction adds a project dependency or edits an existing function.

## Name-owned auxiliary functions

The six exact C# sources in `auxiliary-identities.json` also qualify their
configuration and original source hashes before adaptation. The entity-class
sample's `Counter` type and the entity-function sample's fixed `Counter` function
ID now use the requested main function name. Orchestration activities use the
ID `<FunctionName>-SayHello`, including all activity calls and logger references;
the HTTP starter uses `<FunctionName>-HttpStart`. The C# activity method remains
`<FunctionName>SayHello`.

SignalR's main function ID and logger use the requested name rather than the
fixed `negotiate`. Its connection model is nested as `<FunctionName>ConnectionInfo`.
Dapr's auxiliary methods live directly in the new main class, with method names
`<FunctionName>TopicTrigger` and `<FunctionName>Invoke`, and function IDs and
loggers `<FunctionName>-TopicTrigger` and `<FunctionName>-Invoke`. They are not
nested function classes, which the pinned worker SDK does not index.
The invocation helper's HTTP route is
`<FunctionName>/invoke/{appId}/{methodName}`; its sample curl and Dapr CLI
references use the same requested main function. The external app/method
binding placeholders, pubsub component and topic remain unchanged.

All derived names use native `sourceName` substitution. No existing project
source, namespace, user helper or previously generated route is rewritten.
Raw sources remain byte-for-byte in `provenance/upstream-content/content/`.
Unknown source, configuration or replacement shapes fail packing. These are
intentional authoring changes for newly generated items, not a project
migration or a requirement to upgrade an older compatible package. Older
packages remain usable with their original fixed-helper/repeat limitations.
Unique compiled worker metadata does not establish Dapr/Durable backend
execution or validate deployment-specific routes.

For these six newly authored sources, the CLI also qualifies the exact
source/configuration pair and privately expands native output before writing
the project. It checks the known class/function-attribute layouts, including
the service helper route, rather than deriving an identifier from the filename
or applying a second argv normalizer. Actual generated function IDs must start
with an ASCII letter, contain only ASCII letters, digits, `_` or `-`, and fit
within the host's 128-character limit; `host` is reserved. Orchestrations leave
room for `-HttpStart` (main name at most 118 characters), publishers for
`-TopicTrigger` (115), and service invocations for `-Invoke` (121). Native space
and hyphen normalization is retained; Unicode-only, leading-digit and
leading-underscore IDs are refused rather than producing host-invalid metadata.
Raw older sources retain their existing behavior without a latest-version gate.
Conflicting source proofs or changed canonical sources refuse before writes.
The helper-ID hyphen separates these helpers from native C# primary IDs,
whose `sourceName` normalization converts hyphens to underscores. Thus an
ordinary `Foo_Invoke` primary does not collide with the helper `Foo-Invoke`.
This is not project-wide semantic analysis of arbitrary authored function IDs,
and existing projects are not automatically cleaned up.

## Nullable example models

`nullable-models.json` qualifies seven owned C# model sources and their exact
preceding raw/J/auxiliary adaptation bytes. Fourteen uninitialized string
properties are annotated `string?`: Cosmos DB's `id`/`Text`, SignalR's
`Url`/`AccessToken`, and `Id`/`Description` in Kusto, SQL and MySQL output/trigger
models. These properties already defaulted to null at runtime. No initializer,
required member, null-forgiving operator, serializer attribute or warning
suppression is added. CLR property types, missing/explicit-null JSON behavior
and serialized property names/values remain unchanged.

The Cosmos DB document and Kusto output model also become nested
`<FunctionName>Document` and `<FunctionName>Item`, with every reference
substituted by the native engine. This prevents the same fixed-model collision
when repeating these items or keeping an existing user `MyDocument`/`ToDoItem`.
Original provenance is checked and retained even when an earlier qualified
adaptation already owns the source. No user DTO is inspected or rewritten.
Generated-model integration checks compile repeated items with warnings as
errors and exercise their actual CLR defaults and both supported sample JSON
serializer shapes, without contacting any binding backend.

## Binding string literals

The 36 item configurations contain 23 literal-bearing items with 48 declared
binding parameters. `binding-literals.json` pins their original sources and
complete quoted source contexts. Namespace parameters, authorization choices,
function names and SDK-bound/computed symbols are not string-literal inputs
and are not escaped by this adaptation.

Packing removes only the literal parameters' direct substitutions and adds
native derived symbols using language-specific string-content forms. These
chain the pinned engine's `jsonEncode` form with removal of its outer quotes.
Its escapes (`\\`, `\"`, `\b`, `\f`, `\n`, `\r`, `\t`, `\uXXXX`) are valid
in both ordinary C# and F# string literals; no JSON-only `\/` escape is emitted.
Actual compiler and worker metadata checks separately qualify both languages.
Only exact reviewed quoted contexts receive unique substitution tokens.
SignalR's optional, default-less `HubName` retains its unique original token
so omission still produces the authored `HubValue`, while explicit empty and
nonempty values use the same literal form.
Authored `SELECT * FROM ` prefixes and `/{name}` suffixes remain outside the
transformation. Kusto example comments retain their original text instead of
substituting user input into comments.

Canonical parameters, defaults, help, choices and JSON argument reports retain
the original values. Escaping happens once during native source rendering,
not in argv parsing, the workflow request or generated applications.
Original source bytes remain under `provenance/upstream-content/`; adapted
configuration originals use `template.json.original` there, so the native
engine cannot discover them as competing template definitions.

`binding-literals-qualified.json` pins reviewed adapted configurations and
sources for the CLI. Item preparation reads only the selected package, verifies
the exact association and binds source hashes and the single source output
through the native prewrite snapshot. Changed mappings, derived symbols,
sources or package owners cannot borrow another installed template's proof.
There is no new compiler or runtime dependency during ordinary scaffolding.
The canonical authoring order is supporting types, auxiliary identities, nullable
models, then binding literals. Overlapping source/configuration pairs are pinned
after that composition. Literal, auxiliary and existing caller snapshots are
combined without dropping a proof; mismatched hashes, identities, configurations
or outputs produce a failed preparation. Known qualification failures retain
the normal JSON failure result, while cancellation still propagates.

Older compatible native packages retain their original configuration pins and
can still render plain/default and valid Unicode inputs without newer
provenance, receipt changes, cache migration or automatic update. Values needing
source escaping are refused before writes with explicit selected-package
update guidance. They are never pre-escaped into an old template or silently
rendered with a different compiled binding value. This does not repair
previously generated source or validate a value against a live binding backend.
Unpaired UTF-16 surrogates are refused in both cohorts before source encoding;
they are not valid Unicode and must not silently become replacement characters.
The exact earlier literal-only SignalR source also retains its original fixed
helper behavior rather than acquiring newer auxiliary-name admission implicitly.
The original unfixed MySQL trigger source cannot preserve even a plain table
value because its `table1` token appends an extra `1`. That exact incompatible
source is refused with the same selected-owner update guidance; the corrected
older supporting-type cohort remains usable.

## Deliberately staged

This change does not register or switch public `func init` / `func new`.
The existing stack metadata remains the only stack/language authority.
The current initializer supports only `net10.0`; native integration must
continue to supply that default and reject older/framework targets even though
the unmodified upstream projects contain additional historical choices.
It must not advertise in-process or .NET Framework support.

Native source rendering alone is not parity. Items bind `Framework` through
`msbuild:TargetFramework`; the default func host does not provide that SDK
binding. The internal project planner has an explicit source-fingerprint
qualification for the observed single-root `_gitignore` to `.gitignore`
rename and native-evaluated project filename. It requires an explicitly
supplied `Framework=net10.0`, the installed .NET stack's canonical language,
one generated root project and `host.json`, and the actual native source-to-
output mappings. It rejects additional sources, conditions, include/exclude
rules, other renames, extra project outputs and out-of-root mappings.
The default, unqualified planner still refuses these upstream layouts.
This is an intentional bounded refinement of the previous layout refusal,
not a general relaxation of project topology or name rules.

The internal session forwards this explicit layout through
`ResolvedTemplate.InvokeAsync` only with a controlled dependency capability.
The dependency target must match the actual native-generated project and
invocation root. It previews and validates the native-evaluated action sequence
before creating files, writes mandatory CLI configuration using the existing
create-only writer, rechecks output paths, then executes the ordered typed
package/restore effects. Unknown actions and absent capability remain refusals;
dependency failures retain generated files and configuration with a typed
partial result, never successful completion. Cancellation propagates.

Actual bundled C# and F# resolved-template tests cover this flow, canonical
configuration, exact native dependency arguments, and source/framework/layout/
target/occupancy/interior-link refusals. They substitute only the process runner,
not native rendering, condition evaluation, layout planning or CLI configuration
writes. Existing explicit-root/linked-parent boundary semantics are preserved;
interior output/configuration links, including a project output replaced with
a link during configuration finalization, refuse before dependency execution.
No arbitrary shell/script action executor or public command activation is added.
This project-only flow does not by itself establish item compilation or
host-runtime parity; the separately qualified F# item repair is described below.

The pinned upstream SDK baseline and the actual native-engine/MSBuild
characterization both expose an F# inclusion gap: the HTTP `.fs` file is
rendered, but evaluated `Compile` contains only `Program.fs`. C# includes
the new HTTP source through its default glob. The examined legacy CLI path
delegates item creation to `dotnet new`; no project-item updater was found
in that path. This is source tracing plus an upstream SDK runtime baseline,
not a claim that an old CLI binary was executed.

After restoring unchanged generated dependencies through the repository's
configured feeds, the upstream generated C# app builds and reports the HTTP
function in `functions.metadata`. The corresponding F# app also builds, but
its metadata has no HTTP function because the file is not compiled. A passing
F# project build therefore does not establish item parity. Adding a `.fs`
compile entry before `Program.fs` needs a separately qualified typed project
update; neither package/restore effects nor source rendering supply that step.

## Opt-in F# compile repair

The internal `.NET` updater now supplies that separately authorized operation.
It accepts only the exact selected `.fsproj` digest, its independently
MSBuild-evaluated compile order, and exact generated root `.fs` paths/hashes.
The project must contain direct unconditional literal `Compile Include`
items matching that evaluated order, all defined by the selected project,
with terminal `Program.fs` and `net10.0`. Imported compile entries, globs,
`Update`/`Remove`, conditions, metadata, duplicates and ambiguous partial
inclusion are refused; unrelated project/import bytes remain untouched.

Preview does not write. After native generation, application rechecks source
hashes, links, project bytes and MSBuild order, then inserts the missing entries
immediately before `Program.fs` with a sibling-temp atomic project replacement.
UTF-8 BOM, LF/CRLF, comments, quotes and all original bytes are retained.
An exact already-included sequence is a no-op. Path/digest/cancellation and
commit-time guards do not claim a transaction against an unsynchronized
external editor; changes are checked immediately before replacement.

Explicit item `--force` also permits replacement of exact native-selected root
`.fs` outputs, never project-root cleanup. Preparation captures each existing
regular file's hash and the privately rendered replacement hash. Both dependency
planning passes require force, the exact source/configuration proof, matching
native Change/Overwrite effects and evaluated primary outputs. The engine
rechecks existing target and project hashes immediately before writes, then
verifies native-generated source hashes before controlled effects. Missing,
drifted, linked, directory, inferred or out-of-root targets remain refusals.

An already compiled replacement retains its exact evaluated/direct `Compile`
position, even when later source files follow it; its project bytes are not
rewritten and no duplicate entry is added. An existing but uncompiled file uses
the same qualified insertion-before-`Program.fs` contract. Conditional/imported/
globbed/partially included sequences are not newly supported. The two F# items
without binding parameters have separate original source pins in
`fsharp-control-sources.json`; literal-bearing items reuse their existing
source proofs. No-force conflicts, cancellation and structured source failures
retain their existing behavior.

The original native omission characterization remains a before-state test.
A separate actual native F# project/HTTP integration test applies the updater,
executes the native package reference and restores the exact selected `.fsproj`,
builds the project, and requires the generated function in `functions.metadata`.
This helper is unregistered and does not by itself authorize shared effect
dispatch, source selection, public command activation or a general post-action
rewrite.

## CLI-owned adapter helpers

The CLI explicitly source-links the narrow project preparation, dependency,
F# update and typed dotnet process-helper closure. A host-only compilation
symbol places these same source bodies in a CLI-owned internal namespace;
physical workload namespaces and DI registrations are unchanged. Neither side
casts the other's internal types, and `Func` has no runtime reference to the
physical .NET workload. The full initializer and project factory are not linked.

The framework values and pure source-project file filter are shared once.
The physical factory retains its original top-directory filter, multiple-file
refusal, source-file precedence and prebuilt-output fallback. The controlled
CLI adapter first resolves trusted installed stack/project metadata and then
requires a single source project; it does not adopt the physical output fallback
as template-edit permission.

`upstream-configurations.json` records the exact native configuration SHA-256
values from the two pinned input packages. Packing verifies the same data
against extracted configuration bytes; the CLI embeds this one source to
qualify its bounded adapter, not as a second template or stack catalog.
Installed native catalog selection and installed stack metadata remain the
authorities for availability, language and ambiguity.

`DotNetTemplateWorkflowComposer` now explicitly constructs the CLI-owned
`DotNetTemplateWorkflowProvider` for the internal native runner composition.
It supplies both project and item preparation, not a physical workload service
or a new public capability interface. Project layout qualification is per
candidate in the same native session, so C# and F# can both participate in
ordinary installed-language selection. Names and generated project paths come
from native preparation, not filename synthesis.

For items, the provider requires a trusted containing Functions project from
the installed project resolver, applies the same source-project candidate
filter as the physical workload, and denies missing/ambiguous source projects.
Actual MSBuild evaluation supplies the supported framework, namespace and F#
compile order; the exact project digest is checked around evaluation.
The pinned selected configuration and private native source expansion supply
the effect/source hashes. The fixed capability rechecks source, project and
paths before execution and advances its project snapshot only after owned
dependency/update attempts.

Omitted framework input uses the existing CLI `net10.0` default even though
the upstream template defaults to `net8.0`; explicit unsupported framework
input is rejected. Omitted namespace uses the evaluated project namespace,
while explicit namespace is retained. Both distinctions use the authoritative
canonical explicit-option provenance from the shared argument parser, not a
second alias parser. Except for the qualified literal-derived symbols and additive
F# Cosmos selector, upstream template configurations remain unchanged.

Actual `InitExecutionRunner` and `NewExecutionRunner` tests use this production
provider/composer without private test capabilities for both languages. They
exercise native generation, default/explicit options, trusted metadata,
source/layout/path/refusal and partial/cancellation behavior. Separate tests run
real dependency commands and build both generated HTTP functions into
`functions.metadata`. This composition is not called from default boot or the
public command routes; no rollout, parser or public SDK boundary is changed.

A separate explicit host-factory test installs the actual physical .NET
workload into private homes, uses boot-captured availability and the filtered
installed stack catalog, then calls `CreateInvocation().Composer` for C# and
F# initialization and item creation with request capabilities unset. It runs
the real dependencies and builds each generated HTTP function into metadata.
This exercises the normal workload load-context boundary; the CLI adapter
does not resolve or cast the physical workload's internal helper services.

`DotNetDirectProviderTests` exercises this provider without the deferred common
composer or host factory. Both project candidates share one real native session.
Item preparation uses the physical source-project factory, imported MSBuild
properties and the selected native capture; process controls replace only
dependency execution. Separate integration cases execute real dependencies and
compile C# and F# HTTP functions into `functions.metadata`. Refusal and partial
completion controls retain user files and committed F# compile repairs.

Selected item help uses the same source-pinned adapter to evaluate the trusted
project's namespace default. Unqualified sources or unavailable projects show
an explicitly unevaluated default and diagnostic instead of presenting the
upstream `Company.Function` placeholder as contextual truth. This overlays only
defaults and descriptions; generic help without a selected item does not
evaluate the SDK or dispatch template/dependency actions.

The internal session accepts `FSharpRepair` only for the selected F# item and
an exact evaluated `net10.0` project snapshot. The shared typed planner binds
the repair to that mounted configuration fingerprint and the exact native
create-only `.fs` output/primary-output set. The required compile effect runs
first; package addition and the known args-empty restore action target the
selected `.fsproj`, never the generated source file. Missing opt-in keeps the
original behavior. Unknown restore arguments are not reinterpreted.

An actual pinned F# resolved-item journey exercises this same session path,
the physical updater, real dependency commands and a build that contains the
HTTP function in `functions.metadata`. Separate controls cover preview,
unchanged before-state omission, changed source/project/hash/order contracts,
occupied/repeated outputs, links, cancellation and updater/dependency failures.
Failures after native creation retain the generated source and report a
typed partial outcome; updater failure stops subsequent dependency actions.

The unregistered, internal `DotNetTemplateDependencyExecutor` accepts only an
explicit absolute C# or F# project and a validated literal package reference.
Package addition preserves the SDK's implicit restore; it does not add
`--no-restore`. Restore targets must be resolved by the shared dispatcher.
It propagates failures and cancellation rather than interpreting
`continueOnError` itself. `DotNetTemplateProjectPreparation` uses the existing
dotnet runner to evaluate `TargetFramework` and `RootNamespace`, including
imports, without a build or restore. It rejects unsupported frameworks using
the current initializer's supported-framework list.

The CLI-owned internal `NativeMsBuildBindingSnapshotSource` can bind those
already-evaluated `TargetFramework` and `RootNamespace` values in an explicitly
composed native host. Its immutable input also identifies the exact project,
selected template and source fingerprint; the composing caller must qualify
that selection. It performs no project discovery, evaluation, eligibility
selection or framework fallback, and returns no value for unknown or empty
symbol names. It is not registered in the default native host or physical .NET
workload, avoiding a separate template-engine interface assembly in the
workload load context. Controlled-host tests use the actual adapter with
real imported MSBuild properties and the unchanged upstream HTTP template.
The resolved-item session test also supplies the exact mounted source identity
and fingerprint, verifies the native package-reference effect through the
typed .NET helper, and refuses a missing snapshot instead of accepting the
upstream framework fallback. Dependency process execution is substituted in
that test; it is not a generated-app build or host-run assertion.

Build locally with:

```powershell
dotnet pack src\Workloads\Stacks\DotNet\Workloads.DotNet.csproj -c Release -m:1
```

Restore the declared packages first if they are absent from the normal cache.
The staging step itself uses local bytes only and fails on missing or altered
archives.
