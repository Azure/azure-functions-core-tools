func templates — design walkthrough

Adopting the Microsoft templating engine.
OpenSpec change adopt-ms-template-engine

    The problem

    Two bespoke engines, two formats, one CLI

    Today func new is powered by two templating engines we wrote and maintain ourselves. This change replaces both with the engine that already powers dotnet new — hosted inside our own binary.

    Before

    func new │ ├─► Templates.V2 Node + Python │ custom jobs/actions JSON DSL │ template files inline as JSON strings │ $(TOKEN) substitution, hand-written │ └─► Templates.DotNet .NET build-time down-projection of template.json → dotnet-templates.json scaffold = shell out to `dotnet new` against a provisioned hive delivery: 3 × kind:content workloads gating: channel prerelease labels + sidecar manifest + minBundle tag + pack-time template subsetting

    After

    func new ─┐ func init ─┴─► Templates.Engine (in-process) Microsoft.TemplateEngine.Edge + Orchestrator.RunnableProjects host id "func", isolated hive │ ├─ TemplatePackageManager (install/update) ├─ constraints func-extension-bundle ├─ post actions append │ add-ref │ manual └─ template cache = installed truth delivery: standard NuGet template packages typed FuncItemTemplates / FuncAppTemplates gating: per-template template.json constraints

    What this buys

    • One format. template.json everywhere — the format our .NET templates are already authored in, in a repo we own.
    • No dotnet on PATH. .NET scaffolding stops shelling out; the hive and its provisioning step disappear.
    • Free capability. Conditions, generated symbols, localization sidecars, dry-run, host config files — none of which our DSL has.
    • Ecosystem. Anyone can publish a func template package; search and install come with the model.
    • Less code we own. Two engine projects, a channel mapper, a manifest reader, a hive provisioner, four build scripts and three release pipelines are deleted.
    De-risked. A walking-skeleton spike ran the whole path end to end before any of this was written: 19/19 checks passed. The numbers below are measured, not estimated. (design.md §6B)

    Stage 1 · a fresh machine

    Install the CLI

    A developer installs func and has no templates yet. Nothing is downloaded until they ask for something — except at func init, which is allowed to fetch what the stack needs.

    Three actors, one home. Workloads still deliver the host runtime, workers, stacks and extension bundles. Template packages no longer ride that system — they live in an engine-owned hive next door. That split is the whole pivot (D21).
    ▶Under the hood — where state lives, and why isolation was the tricky bit disk layout · C#
    Spike-verified: after a full install → list → scaffold → uninstall cycle, the modification time on ~/.templateengine was unchanged.

    The engine scopes its settings by host identifier and by a global settings directory. Overriding only the host id still shares the global path with dotnet new — the spike caught this.

    FuncTemplateEngineHost : ITemplateEngineHost Identifier = "func" → reads func.host.json from templates Version = CLI version Components = fixed at construction (nothing loads from packages) │ ▼ EngineEnvironmentSettings IPathInfo → FuncTemplateEnginePaths (the hive, above) IEnvironment, ComponentManager │ ├─► TemplatePackageManager install · uninstall · update · scan ├─► TemplateCreator dry-run (GetCreationEffectsAsync) · instantiate └─► TemplateConstraintManager evaluates func-extension-bundle, host, os

    Built lazily on first use and kept alive for the process — the first scan is the expensive one.

    Stage 2 · create the project

    func init — now template-powered

    The wizard gains one new step: which project template? The default Empty reproduces exactly what init produces today, so the default path feels unchanged.

    What stayed the same

    • Stack and language selection, and the resulting file set for Empty.
    • .func/config.json is still written by init itself — templates never author CLI config.
    • The stack workload is still required before init can run.

    What is new

    • A project-template step, filtered to the chosen stack; --template skips it.
    • Auto-install of the stack's official packages when missing (offline gives an actionable error).
    • .NET init no longer shells out to dotnet new func.
    • Per-stack init options now come from the template's own symbols.
    ▶Under the hood — the Empty template, the shrunken stack contract, and the init pipeline json · C# · flow

    The PythonVersion choice symbol is the whole point of D31: it hydrates into func init --python-version using the same code path as a func new option — no stack-workload code involved.

    The stack workload stops scaffolding and becomes a metadata record. Two members go away; one is added.

    func init 1. resolve stack ← installed stack workloads' metadata 2. resolve language ← wizard / --language 3. ensure packages ← OfficialTemplatePackageIds not installed? online → install, print a message (D27) offline → actionable error, name the pkg 4. select project template installed app templates + index results for this stack --template <id> bypasses · non-interactive defaults to Empty 5. hydrate options ← the template's symbols, same hydrator as func new 6. engine scaffold ← TemplateCreator.InstantiateAsync 7.     Stage 3 · discover what I can add

    The catalog comes from the engine cache

    Same output the user knows — but every row is now derived from a real template.json, read from a cache that works with the network unplugged.

    Ids changed; acceptance did not. The catalog now shows short, language-free ids. HttpTrigger-TypeScript and friends stay valid as hidden aliases, so existing scripts and muscle memory keep working. (D8 → D19)

    The engine persists derived metadata for every template in every installed package, and reconciles before serving a query.

    • Rebuild triggers, in order: unparsable file or format-version mismatch, locale mismatch, a mount with a newer timestamp, or a changed mount-URI set.
    • Scoped per CLI version, so an upgrade costs exactly one cold scan and can never read a stale-format cache.
    • Deleting the directory is always safe — worst case is one rescan.
    func new pipeline — 13 steps today, 11 after 1. resolve profile unchanged 2. resolve project (hard gate) unchanged 3. validate stack unchanged 4. select templates workload ← channel matching DELETED (D16/D21) 5. resolve language unchanged 6. list templates ← engine cache query, was: aggregate providers 7. resolve template ← shortName match or picker 8. hydrate options ← live parameter definitions, was: two bespoke readers 9. re-parse with hydration unchanged 10. resolve function name unchanged 11a. validate bundle presence unchanged 11b. validate minBundleVersion DELETED — constraints subsume it (D16) 12. apply ← engine dry-run + instantiate, was: dispatch by EngineId 13. render unchanged

    Today a malformed entry can take down a whole stack's catalog. Under the engine, scanning is per template.

    Stage 4 · what can I configure?

    Every template input is a real CLI option

    The user types --help for a specific template and sees native options with completion, choice validation and error text. Adding a new input to a template requires no CLI release.

    Every prompt is an option. No -p key=value catch-all, and options are strictly template-scoped: passing --file to a Node template is a normal unrecognized-option error, because only Python templates declare that symbol.
    ▶Under the hood — symbols to options, and the file that names them flow · json · C#
    argv: func new -t http -n GetOrders --auth-level ANONYMOUS stage A parse only the built-in options └─ read --template http │ ▼ resolve template in the engine cache │ ▼ hydrate: ITemplateInfo.ParameterDefinitions + func.host.json (longName · isHidden · validator) + stack default function-name validator │ ▼ attach real Option<T> instances to the `new` command │ stage B re-parse the original argv — now --auth-level is a first-class option with choices, a default, help text and tab completion

    Identical mechanism to what ships today; only the metadata source changes — from a build-time projection and a hand-written prompt catalog, to the live engine cache.

    The engine ignores unknown host files, so this is func-private metadata that travels with the template. It is what turns AccessRights into --auth-level.

    Ground truth check. We assumed func could inherit option names from upstream dotnetcli.host.json files. There are none — the corpus has only VS host files, and dotnet new has always used raw symbol names. Since we own that repo, func.host.json is contributed at the source for .NET too. (D10)

    What the hydrator reads for the real upstream HTTP template — note the raw symbol name that D10 exists to rename.

    The spike loaded this template from nuget.org and confirmed the parameter set arrives intact: http → namespace, AccessRights.

    Stage 5 · the common case

    Scaffolding a new file (Node, .NET)

    Most templates create files. The engine dry-runs first, so conflicts are detected before anything is written.

    ▶Under the hood — dry run, sourceName, and what "Created" means flow · C#
    ApplyAsync(template, name, options) │ ├─ 1. GetCreationEffectsAsync ← dry run: file operations, no writes │ any create collides with an existing file and no --force? │ → AlreadyExists failure, exit non-zero, nothing written │ ├─ 2. InstantiateAsync ← stage-B parameter values │ --force maps to the engine's overwrite mode │ ├─ 3. post actions ← host-side dispatch by ActionId (stage 6) │ └─ 4. report Created: (engine outputs) ∪ Modified: (post-action effects)

    The conflict gate is scoped to template outputs. Post-action effects — a csproj edit, a Python append target — are not conflicts; those processors are written to be idempotent.

    One mechanism replaces the V2 engine's filePath action arguments and its content token substitution.

    Engine statusMapped CLI failure
    Success—
    MissingMandatoryParam, InvalidParamValuesInvalidPrompt
    CreateFailedWriteFailed / ProviderError
    NotFoundunknown-template error + catalog hint

    The typed failure hierarchy the CLI already renders is preserved; only its inputs change.

    Stage 6 · the case that needs more than files

    .NET: the scaffold that edits your project file

    An isolated-worker function needs an extension package reference, at the version that matches the project's target framework. Today dotnet new does that for us. In-process, we have to do it ourselves — and this is the part the design nearly missed.

    Discovered by ground-truthing, not by design. Reading the real corpus showed isolated templates depend on two things the engine does not give a host for free: the add-reference post action, and an msbuild: bind source. Without both, .NET scaffolds are silently broken — wrong package version, or no reference at all. (D11 amends D6)
    ▶Under the hood — the real upstream template, and how the host answers it real json · C# · dispatch table

    Unedited from the repo we own. Note the bind symbol, the computed TFM predicates, and three conditional post actions choosing package versions.

    Empty ManualInstructions is the tell: if the host does not implement the action, the user is told nothing at all. That is why it had to join the allowlist.

    Spike correction. The engine has no IPostActionProcessor component model. It returns ICreationResult.PostActions; the host runs its own code keyed by ActionId. The allowlist is therefore a switch we own — templates cannot introduce executable behaviour at all. (D32 refines §2.6)

    The engine ships host: and env: bind sources. msbuild: comes from the dotnet new CLI host — so func must supply its own or every TFM predicate silently falls back to the template's default.

    Stage 7 · the hardest case

    Python v2: adding a function to a file that already exists

    Python's programming model registers functions on a shared app object. The engine has no "append" primitive — it materializes file trees. This was the one risk that could have sunk the whole design, so it was spiked first.

    Flow matrix

    InvocationTarget stateBehaviour
    no --filefunction_app.py existsappend, bound to app
    no --filefunction_app.py missingcreate with the full app header, then append — v4 parity, forgiving of a deleted file
    --file api.pymissingcreate as a blueprint (bp = func.Blueprint()) and print registration instructions — no auto-edit of the user's Python
    --file api.pyexistsappend, bound to bp
    anytarget already defines def get_orders(hard error — --force does not override
    All four flows passed the spike, including staging isolation and duplicate rejection. The V2 engine expressed this as four near-duplicate jobs per template; it collapses to one template and one snippet. (D13, SP-2)
    ▶Under the hood — one snippet, one post action, a staging directory json · python · flow
    • --file is not hardcoded in the CLI — it is the func.host.json alias of the AppFile symbol. Any stack can adopt append semantics by declaring the same shape.
    • The flow keys off the post action, not the stack.
    • Blueprint is not a separate catalog row — one template per trigger, --file routes the flow.

    sourceName renames HttpTriggerFunc; APP_OBJECT becomes app or bp depending on the flow the CLI resolved.

    Authoring rule: snippets assume the standard preamble (import azure.functions as func, import logging) and must not require new imports — we do not rewrite the user's import block.
    func new -t http -n get_orders │ ├─ engine instantiates into a provider-owned staging directory │ %TEMP%/func-scaffold-a1b2/__snippet__.py ← not the project │ ├─ append processor │ resolve target ← AppFile (explicit --file or default) │ duplicate guard ← scan for `def get_orders(` → error if present │ create vs append ← header written only when creating │ append with separator hygiene │ delete staged file │ report target as Modified: │ └─ failure? the project is untouched and the staged snippet is named in the error for manual recovery

    The engine's dry run cannot see the append, so the provider adds the append target to its own conflict and reporting logic.

    The same package can be consumed by hosts that do not implement our action — Visual Studio, dotnet new. They do not fail; they fall back to the author's text.

    Stage 8 · "why can't I see that template?"

    Availability is declared by the template, evaluated per project

    A trigger whose binding only exists in newer extension bundles should not be offered to a project pinned to an older one — and when the user asks for it by name, they should be told exactly what to change.

    This one decision deleted a lot of machinery: the channel axis (stable/preview/experimental prerelease labels and per-channel packages), the templates-workload.json sidecar, the minBundle: nuspec tag, the channel-match pipeline step, two failure modes, and the entire Node pack-time subsetting pipeline (CDN index fetch, HTTP-Range zip extraction, binding cross-reference). (D16)
    ▶Under the hood — a constraint, a component, and three contexts json · C# · table

    Right granularity (per template), right owner (the template author), and it travels with the package — a community template can declare its own bundle requirement with no CLI involvement.

    ContextBundle used
    func new (list, help, scaffold)the project's resolved bundle from host.json
    func init surfaceslatest available bundle — no project exists yet (D30)
    a foreign host (VS, dotnet new)component not loaded → template treated as restricted, not an error
    Before host.json bundle id → channel (stable|preview|experimental) → pick the templates workload whose prerelease label matches → read templates-workload.json → compare minBundleVersion → hard error after selection pack time: subset Node templates per channel by cross-referencing the CDN bundle's extensions.json
    After host.json bundle → evaluate each template's own constraints → unmet = hidden from selection, retained for the call-to-action pack time: nothing. One package per stack ships every template; visibility is decided at invocation.
    Stage 9 · templates we did not write

    Discover and install any func template package

    Because packages are now standard NuGet template packages with a func package type, anyone can publish one — and the CLI can find it.

    Search and install do not need a project. Lifecycle modes bypass the project and profile gates — searching before you have anywhere to scaffold is the normal case. Listing and scaffolding still require an initialized project. (D30)

    Indexing is driven by NuGet package type, not by name conventions, tags or an allow-list. This is the mechanism that makes third-party func templates discoverable at all.

    So the func index is produced by substituting the query string — the rest of the machinery is untouched:

    Implementation note. The query set is a hard-coded dictionary keyed by an internal enum, and the feed URL is a constant. Adding func's package types therefore means either an upstream contribution (make queries/feed configurable) or a small func-owned fork of the tool. Either way the scanning, prefiltering, diffing and cache-writing code is reused as is. Sequenced as task 3.5.2.
    Why the package-type query matters for scale. The NuGet search API caps at skip 3000 / page 1000 — the tool can retrieve at most 4000 packages per query and warns when a query exceeds it. packageType=Template is close to that ceiling; packageType=FuncItemTemplates returns a handful. Our index stays small, fast and complete.

    Three prefilters run before a package is downloaded and scanned. They are the reason the index stays clean and the daily run stays cheap.

    PrefilterBehaviour
    TemplateJsonExistencePackFilterDrops packages containing no template.json at all. Disabled with --noTemplateJsonFilter.
    SkipTemplatePacksFilterSkips packages already recorded in nonTemplatePacks.json from earlier runs.
    FilterNonMicrosoftAuthorsAnti-spoofing. If a template declares "author": "Microsoft" but the package id does not start with the reserved Microsoft. prefix, the package is filtered out.

    Our official packages keep the Microsoft. prefix, so they pass; a community package impersonating Microsoft authorship never reaches the index.

    The published artifact is the engine's own search-cache format — version 2.0. It is a reverse index: packages, each carrying the template metadata needed to display a result without downloading anything.

    • Our stack/trigger tags ride along in TagsCollection for free, so search results can be filtered by stack the same way the local catalog is.
    • Reserved and TotalDownloads are the signals to surface when showing third-party results.
    • IAdditionalDataProducer (used upstream by CliHostDataProducer to embed dotnetcli.host.json data) is the hook if we ever want func.host.json data in the index too.

    Stage 10 · living with it

    Updates are explicit; offline always works

    Everything a user needs to list and scaffold is on disk. The network is used for exactly four things: search, install, update, and init's first-run acquisition.

    OperationNetworkProject required
    func new --list, --help, scaffoldneveryes
    func new --searchindex (or cache / local override)no
    func new --install / --uninstall / --updateinstall and update onlyno
    func initonly when official packages are missingn/a
    ▶Under the hood — rollback, concurrency, and the upgrade path semantics
    • Rollback is an explicit install of an older version (func new --install pkg::1.0.0). There is no workload-style side-by-side "highest wins" any more — the engine's store holds one version per package, which is also what makes the cache honest.
    • Concurrency (spike SP-3, still open): two simultaneous installs, and an install landing between cache reconcile and query, need cross-process locking around hive writes. Tracked as an implementation task, not a design risk.
    • CLI upgrade uses a version-scoped cache directory, so a new CLI pays one cold scan and can never read a stale-format cache; stale sibling directories are cleaned opportunistically.
    • The old dotnet template hive from the pre-change CLI is left on disk and documented in release notes — it is inert, and only exists on v5 preview machines (D14).
    Stage 11 · when things go wrong

    Failure paths, and why a template package cannot hurt you

    The typed failure UX users already know is preserved. Three failure modes disappear entirely, and two new safety behaviours appear.

    Failure inventory

    FailureStatus
    Not a Functions project → run func initunchanged (list/scaffold only)
    Unknown template idunchanged — and less likely, thanks to legacy aliases
    File already exists → --forceunchanged, now driven by the engine dry run
    Missing / unresolvable extension bundleunchanged hard error
    No templates installed for this stackinstall hint; func new never auto-installs
    dotnet not on PATHdeleted — nothing shells out
    Template hive missing / partially provisioneddeleted — no hive
    Five-minute provisioning timeoutdeleted
    No templates workload for this channeldeleted — no channels
    minBundleVersion too oldreplaced by constraint gating with a call-to-action
    Malformed template.json in a packagenew — that template is skipped with a [packageId] warning; the catalog survives
    Post action failednew — warns with manual steps when continueOnError, otherwise a typed failure

    Security posture

    Template packages are data. The engine component set is fixed when the host is constructed. No assembly, generator, macro or post-action processor is ever loaded from an installed package; unknown post-action ids are not executed; unresolvable components fail that template's use with a diagnostic rather than loading anything.
    • Scanning a package is template.json parsing — the spike confirmed no payload code executed on the first pass.
    • The run-script post action is deliberately not dispatched, even though the engine format supports it.
    • An adversarial test (malicious component pack and a payload assembly) is an implementation task, not an open design question. (SP-4)
    Stage 12 · the other user

    Authoring a template

    Two audiences: our own teams converting the existing corpus, and third parties shipping their own triggers. Both use the same format and the same publish path.

    Adding an input to an existing template — the whole change

    func new -t queue --help shows --max-retries immediately, with type checking and a default. No CLI release, no schema change, no code. That was the goal all along; it now holds with zero bespoke schema on our side.

    Internal conversion pipeline

    StackWorkOngoing
    NodeConvert 33 in-repo V2 entries to template folders (inline files → real files, $(FUNCTION_NAME_INPUT) → sourceName, prompts → symbols), then hand-finish per templateAuthored here, as today
    PythonAuthor from the extension bundle's Python corpus as snippet + append post actionChanges ownership: updates flow through this repo instead of riding bundle republishes — needs Python owners' sign-off
    .NETNo authoring. Add the func package types and func.host.json at the sourceUpstream, unchanged

    Content is authored in core-tools while it churns, with a declared end state of migrating the finished trees to Functions.Templates so every stack follows the .NET model. (D12)

    Authoring loop upgrade: the engine diffs mount timestamps, so editing an installed template in place is picked up on the next func new — no reinstall, no repack while developing a template.
